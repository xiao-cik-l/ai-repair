# 评测：报修分类

这个文件夹只有一个问题要回答：**「改完之后到底准了没有？」**

没有标注样本，所有优化都只能靠感觉，而感觉不是结论。有了这里的文件，改前跑一次、改后跑一次，两个准确率一比，改动是赚是亏一目了然。

## 文件清单

| 文件 | 是什么 | 要改吗 |
|---|---|---|
| `eval_cases.py` | **评测集**：24 条人工标注的报修句，每条标好正确的 `category` 和 `urgent` | 扩样本时改这里 |
| `eval_classifier.py` | **评测脚本**：逐条调 `classify_repair()`，算出三组准确率并列出判错的条目 | 一般不用动 |
| `eval_result_before.txt` | 优化前的成绩存档（10/14） | 只读，历史证据 |
| `eval_result_after.txt` | 优化后的成绩存档（10/14） | 只读，历史证据 |

## 怎么跑（任意目录下都能跑）

```bash
# 冒烟测试：只跑前 2 条，先确认通路正常、少花钱
D:/py/python.exe "02_报修分类/评测/eval_classifier.py" --limit 2

# 正式跑：全跑一遍，结果存成 eval_result_<tag>.txt
D:/py/python.exe "02_报修分类/评测/eval_classifier.py" --tag before   # 改动前
D:/py/python.exe "02_报修分类/评测/eval_classifier.py" --tag after    # 改动后
```

`--tag` 就是结果文件的命名后缀。**改前用 `before`、改后用 `after`**，两个文件摆在一起就是「这次优化有没有用」的凭据。

会**真实调用大模型 API**（24 条，费用可忽略）。结果同时打印在终端并存成 txt。

## 输出的三组数字

| 指标 | 含义 |
|---|---|
| `category` 准确率 | 类别分对了多少 |
| `urgent` 准确率 | 紧急程度判对了多少 |
| **完全正确率** | 两个字段都对才算整条对（**最严格，看这个**） |

## 10/14 那次的成绩

以 24 条样本为准，前后各真实跑一遍：

| 指标 | 改前 | 改后 | 变化 |
|---|---|---|---|
| category 准确率 | 91.7% | **100.0%** | +8.3pt |
| urgent 准确率 | 75.0% | **91.7%** | +16.7pt |
| 完全正确率 | 70.8% | **91.7%** | +20.9pt |

改动前 7 条判错，集中在两类可预见的缺陷：

- 「墙上有个裂缝」→ 被判成**门窗**、「天花板往下渗水」→ 被判成**水管**：当时模板里只有四个类别，**没有兜底类**，模型只能硬塞
- 「宿舍的灯不亮了」「空调不制冷」→ 被判成**紧急**：当时模板里**没写紧急的判定标准**，「急不急」全靠模型猜

改后残留 2 条：

- 「马桶水箱一直在响」→ 模型判紧急，标注是不紧急
- 「墙上有个裂缝，一直掉渣」→ 模型判不紧急，标注是紧急

**这 2 条是标注规则本身有模糊地带**（「一直响」算不算影响使用、「掉渣」算不算坠落风险），不是模型能力问题。规矩是：先把评测集扩到 50 条左右再看，不为了凑满分去改 prompt —— **24 条样本上硬调就是过拟合**。

## 标注口径从哪来

`eval_cases.py` 顶部的注释写明了类别定义和「紧急」的五个条件，**与 `01_公共模块/prompt_templates.py` 里 `repair_classify` 模板的规则一一对应**。

⚠️ **两边必须同步**。改了模板里的类别或紧急规则，`eval_cases.py` 的口径注释、`02_报修分类/classifier.py` 里的 `CATEGORIES` 常量都要跟着改，否则评测会把模型的正确答案判成错的。

## 三条使用纪律

1. **改 Prompt 之前先跑 `--tag before`** —— 没有基准，改完无法判断是赚是亏。
2. **改规则要三处同步**：模板（`prompt_templates.py`）、允许取值（`classifier.py` 的 `CATEGORIES`）、标注口径（`eval_cases.py` 注释）。
3. **评测集越大越可信，但别为了凑分调 Prompt**。样本少的时候，准确率的多寡主要是噪声；重点看「判错的那几条，错在同一个原因上吗」。

## 样本怎么扩

照着 `eval_cases.py` 里 `CASES` 的格式往下加就行，每条一行：

```python
{"text": "洗手池下水特别慢，积一池子水", "category": "水管", "urgent": "否"},
```

建议从这三个来源补：**自己瞎编容易漏场景，真实语料才有价值。**

- 你自己和同学实际报修过的说法（口语、错别字、不带标点都保留）
- 宿舍维修系统 `repair_orders` 表里已经存在的工单描述 → 直接当语料
- 边界样本：既像电器又像门窗的、描述里只说「坏了」不说是什么的

## 这套东西还能复用

结构是通用的，换 `eval_cases.py` 的内容、换被测函数，就能拿去评 RAG 问答（命中率 / 拒答率）或建单（字段抽取正确率）。毕设那边也能直接搬。
